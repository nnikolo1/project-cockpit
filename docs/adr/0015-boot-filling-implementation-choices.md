# 0015. Boot-filling job: implementation choices beyond ADR 0014

Status: proposed (builder, task PC-19); the owner confirms or changes
Date: 2026-11-20
Modules: internal/bootfilling

## Decisions
- One poll is one short process started by launchd every `poll_minutes` (default 10, owner 2026-11-20; `--once`); no resident loop. State lives in `state-<mode>.json`, so the dry run and the real mode never share fired-window or day counters.
- A window is identified by its `resets_at` (rounded to 10 minutes). A trigger fires at most once per window. When the larger 5-hour trigger wins it also marks the smaller one as fired; nothing is marked when the day cap leaves 0 tasks, so a later poll can still fire.
- The kill-switch label `pause` is read from the tracking issue (the same issue that receives the daily summary); the flag file is `PAUSE` in the data folder.
- Eligibility is opt-out with conservative defaults: labels `type:decision` and `question`, a title pattern for send, submit, withdraw, delete, drop, spend, purchase, schema, DDL, plus a per-project file (labels, numbers, title patterns). Over-excluding is the safe error; all are configuration.
- Tasks of all configured projects are ranked together; ties inside the group that straddles the cutoff are the only ones sent to the model judgement (titles and keys only); a failed judgement keeps the task-number order and records the failure as the reasoning.
- Workers are detached `sh` processes that write an exit-code file; a later poll reaps them. A non-zero exit puts the task back into the queue once (`max_attempts`, default 2) and the retry is logged as `resumed`. Worker start stops when either window has `worker_stop_left` percent or less.
- Two decision logs: the contract file `decisions.jsonl` in the budget folder (docs/contracts/budget-panel.md, poll and release lines) and the job's own richer `decision-log.jsonl` (ranking inputs, outcomes per task). The budget list of released tasks is `core.release_list` over the richer log.
- The release uses the cockpit's own label edit (`cockpit._edit`, `cockpit.execute`) and refuses when `gh` is not logged in as the Manager.

## Limits
- The "no network except the hosting CLI" rule for workers is not enforced by stdlib code; the tool allowlist is. An operating-system sandbox is an open point.
- Poll interval: key `poll_minutes` (default 10). Nothing in the logic depends on the interval: windows are keyed by `resets_at` (rounded to 10 minutes) and a trigger fires once per window, the daily summary is once per date, and the day counter rolls by date. The one derived value is the budget panel's stale limit for the quota reading, three polls (`cockpit --quota-stale-min`, 30 for the default); `python3 -m bootfill.render_plist` renders the launchd plist from the template and the config and prints the matching flag. It never loads anything.
- Idle means that no Claude Code agent other than the job's own is active (owner, 2026-11-20). Own calls are made from a dedicated working directory (`<data dir>/headless`, key `headless_dir`), so their transcripts land in a separate folder that is excluded from the transcript scan, as are the worker worktrees (`transcript_exclude`, default `*-wt-boot-*`). Own workers never block a poll. Other activity: a Claude Code transcript written within `idle_minutes` (only `~/.claude/projects`, the Claude Code folder), or a headless (`-p`/`--print`) process whose executable is exactly `claude` (`process_names`, `process_exclude` removes the desktop app, the browser and helpers) and that is neither the job nor a descendant of the job or its workers. Interactive sessions are judged by their transcript only. When `ps` fails the poll log says "process check unavailable: transcript signal only". An age below zero (a transcript timestamp after the poll's clock reading) is clamped to zero.
- Conflict-aware choice (owner, 2026-11-20): the queue keeps rank order. When a slot frees, the first `conflict_window` (6) queued tasks are scored against the running and already chosen tasks by cheap signals: different project (never conflicts), a shared path named in the issue, a label from `conflict_labels` on both, same module (+3), same top-level module (+2), same project (+1); a score of `conflict_threshold` (3) or more means "would get in the way". The head is taken unless it conflicts and a later one does not; a task passed over `conflict_max_skips` (3) times is taken at once. Only when the signals are unclear (module unknown and no paths) is the model judge asked, with keys and titles only; a failed judge falls back to the lowest score. Each choice that skipped or had company is appended to `decision-log.jsonl` (type `conflict_choice`: chosen, skipped, signals, reasoning).
