# Background digest: what happened so far (context for the research, not requirements)

Shortened by the owner from the assistant's draft, 2026-11-22 (spelling lightly corrected). Background only: facts and decisions as they occurred in the working sessions of 2026-11-15 to 2026-11-22. Generic wording (public repository).
Modules: docs

## How the Project cockpit grew

- Mid-November: the owner, working with the assistant in interactive sessions, lost track of what had been discussed and built. A written problem statement asked for what a ticketing board gives (backlog, kanban, priorities, deadlines, who is doing what) without adopting a hosted tool (cost, and a second place for the truth). Owner decisions: tasks live as GitHub issues; the cockpit is a thin local client over them; it is public and meant to serve every project of the owner, and to be the template for new ones.
- Phase 1 was deliberately simple: everything acts as the owner's own GitHub login (no separate identities), labels carry the state (released, priorities, deadlines), only the owner releases tasks. Known shortcut: authority cannot be enforced, only detected.
- The cockpit then grew several displays: tasks and a backlog, open questions, rules and decisions, a code-activity and persistence view per module (generated by collectors from the project's repository), and a budget tab.

## The roles as practised

- Manager (the owner); Personal Assistant (an interactive assistant session that does what the owner asks, including formulating tasks); Orchestrator (a privileged agent role that releases tasks, analyses them and integrates results: the manager and janitor pattern); Worker (a headless assistant session that takes one task, commits in its own git worktree, and has the narrowest rights).
- Owner decisions on workers: least privilege; inserts and updates in the database are acceptable, deletions and table-structure changes need the owner's approval; a worker marks its task in progress as its first action; no automatic retries; a task is worked at most once unless the owner or Orchestrator requeues it.

## The unattended job (boot-filling) as built, 2026-11-20

- Idea (owner): when no other assistant session is active and the quota is about to expire, release ranked tasks automatically and let workers use the quota. Triggers: more than 10% of the 5-hour quota left in the last 2 hours of the window releases 5 tasks; more than 50% releases 20; more than 20% of the weekly quota with one day left releases 50; a day cap of 60; 2 workers at a time; one poll every 10 minutes; a laptop that may sleep (a keep-awake step was added; a closed lid still sleeps the machine).
- Implementation: a scheduled script reading the issues through the cockpit's own code, a JSON state file, guards in code, labels and assignees as state, headless sessions as workers with a tool allow and deny list, and a quota reading taken from the assistant's status-line file (valid only while an interactive session runs; otherwise estimated from token counts in the session transcripts).

## What happened in the first real run (the night of 2026-11-20 to 2026-11-21)

- The hosting service returned silently incomplete label-history data for large queries; the released labels looked unauthorised and were dropped; already released tasks looked unreleased and were released again in every trigger window: 4 batches of 20, 77 worker runs, 29 draft pull requests nobody had reviewed, and weekly token use rising from about 1.14 to 1.58 billion.
- Other incidents: a worker hung for 1 h 53 min with no output (no time limit existed); a worker wrote 61 rows into a real database through a symlink placed in its worktree; most pull requests edited the same shared report file and would conflict; the quota readings were wrong while the owner was away (the status-line file is not updated by headless sessions; a missing 5-hour window was read as a fresh empty window); the laptop slept with the lid closed for about three hours.
- Fixes made afterwards: paging and repair of the history queries; guards (never release a task already carrying the released label, never start a worker twice, no retries); worker rights reduced to local commits (the job pushes the branch and opens a draft pull request); a worker rules block; stale-quota estimates labelled as estimates; the job is paused until a decision on the architecture.

## Observations and design ideas raised along the way (owner and assistant)

- Two states matter: released (a queue entry, constrains nothing) and in progress (from a worker's start until the Orchestrator or owner accepts or rejects the result, which can take days); only in progress should limit which other tasks may start.
- Combinable tasks ("salvos"): sets of tasks that do not interfere; "interference" must not be defined so strictly that workers starve; hot shared files (reports, migrations) are incidental conflicts.
- Where control belongs: static clearance once before release (may this task run unattended at all), dynamic checks at every start; undecided.
- Review and acceptance capacity may be the true bottleneck, not quota.
- A single source of truth versus a local store: considered because the hosting service could be unreachable; the owner now thinks that case unlikely (a fully offline laptop cannot reach the model service anyway) and sees a second store as a compromise, not a principle; open to being challenged.
- Principles the owner stated: adopt over build (open to challenge); fail clearly (every dead end visible with its reason and the action needed); every state and transition explainable in one plain sentence; no unexplained mechanisms; the owner (possibly via the GUI of the Project Cockpit, or through an interactive session) keeps authority over releases, deletions and structure changes.
- Plans noted but not built: separate identities for Manager, Orchestrator and Worker on the hosting service; an operating-system user or sandbox for workers (tool lists alone cannot restrict what python or pytest can do); roles for database access.

## What is not known

- How long review and acceptance really take per result; how well the read and write sets of a task can be predicted from its text; whether the hosting service gives read-after-write consistency on labels and comments; how the quota windows are measured by the provider.
