# Roles and privileges for the Worker and the Merger (PC-38)

Date: 2026-11-28
Modules: internal

How the discussion of 2026-11-28 ended on separating the privileges of the Worker and the Merger. It extends [Roles and identity](2026.11.17-roles-and-identity.md) and is the working note for PC-38 (identity separation on the hosting service).

## Why now

The owner asked for Merge Workers (PC-155): an hourly job that merges every `unmerged` task without DDL; changes to policy or to settings are off-limits to it too. Question PC-154 records the owner's answers: the merge authority is extended to a scheduled Merge Worker, and it first runs as a host job under the owner's own login, a temporary solution. A job that holds the owner's whole login can do anything the owner can, so the Worker and the Merger need different roles and the question of PC-38 has to be settled "anyway" (owner, 2026-11-28).

## Roles

| Role | May | May not |
|---|---|---|
| Worker | push to its own task branch, comment, report its task as awaiting merge | merge, create tasks, release, set labels |
| Merger | merge a task branch into the main branch when the checks pass; file a follow-up task when they fail | merge DDL, policy changes or setting changes; release; accept |
| Owner | everything, including release and the approval of DDL | |

## Decided (owner, 2026-11-28)

- **Recognition of what the Merger may not merge** (PC-154, closed): a deterministic check, a committed and tested script run on the task's diff: an exhaustive list of DDL statements, fixed path lists for policy and settings files. It is part of PC-155.
- **Now: separate accounts or tokens per role on the hosting service, plus branch protection** on the main branch (only the Merger's identity merges, with the checks required; files that hold policy and settings are under code-owner review, which the Merger cannot satisfy). This is a temporary solution.
- **Eventually: a gate that holds the credential and exposes only role-limited actions, and/or a database of workflow state with roles.** Not decided between them or in what order.

## Options (analysis, not decisions)

1. **The hosting service only.** Cheap and uses what exists. Weakness: labels and issue edits cannot be restricted by role, so the protected-label rule stays after-the-fact.
2. **A gate.** A small local service holds the credential; agents ask it for role-limited actions and never see a token. Strongest per role; new code.
3. **A database of workflow state.** One row per task, forward-only transitions, roles in the database; the hosting service keeps the content and shows labels as a one-way projection. Solves labels as well; needs a schema, a backup and the owner's approval of the DDL. See the design thread in [the pause memo](2026.11.27-pause-and-how-to-resume.md).

## Findings on option 1 (research of 2026-11-28; from the hosting service's documentation and community pages, not tried out)

- **Branch protection and rulesets:** on the free plan they are available for public repositories only; for private repositories they need a paid plan ([about rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets), [community discussion](https://github.com/orgs/community/discussions/174419)). So option 1 works for a public repository (this one, whose main branch is not protected today) and not for a private one without a paid plan. The owner's plan is not readable through the API.
- **Code-owner review:** it is a setting of the same pull-request rule, so I expect the same availability; no source says so outright (unverified).
- **Second account:** the terms allow one free machine account next to a personal account, used only for automation and with a human accountable for it ([terms of service](https://docs.github.com/en/site-policy/github-terms/github-terms-of-service), [community discussion](https://github.com/orgs/community/discussions/189661)). A second personal account is not allowed. One machine account covers one extra role (the Merger); the Workers keep their narrow token. A GitHub App is a further identity that is not an account (not researched).
- **Not found, to test on a throwaway public repository:** whether, on a user-owned repository, a rule can let only one identity merge. Organisation-owned repositories have more controls than user-owned ones, and I could not confirm what a user-owned repository allows.
- **Credential reach:** the host job must run as the Merger's account without the owner's login being readable by the agents' processes (separate OS users share a disk, see the earlier memo).
