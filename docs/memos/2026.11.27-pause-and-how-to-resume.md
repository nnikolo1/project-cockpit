## The design thread that keeps coming back: where workflow state lives

A second assistant's analysis (2026-11-27), recorded as thinking, not decided:
- Hosting-service issues are built for discussion, not as a state machine: any combination of labels is possible, anyone with write access can set any label, labels cannot be restricted by name, reads can be thinned silently, label swaps are not atomic.
- Derive what can be derived and store only real decisions: "merged" is a fact about git, "running" a fact about a process; what remains to store is small (released, accepted, rejected, requeued, and who decided each).
- A way without two-way synchronisation: a database owns workflow state (one row per task, forward-only transitions, an event history, constraints for "one state" and "allowed transitions"); the hosting service owns the content (task text, discussion, pull requests); labels become a one-way projection written from the database and never read back as truth.
- Permissions get easier: roles in the database (a Worker may only move released to in progress to awaiting acceptance; only the Orchestrator or the owner accepts), one mechanism for the identity separation (PC-38), the no-network question (PC-27) and the database access-model question of the private project.
- Costs: the Cockpit becomes the place to see and change status; a schema (the owner's approval of DDL applies) with a backup; Workers need database access, which ties to a separate account for them.
- A cheaper middle step: a single-select status field of the hosting service's project boards guarantees exactly one state per task but enforces neither transitions nor permissions.
- PC-37 (cancelled: a local ledger of the job's own actions) would become "the owner of workflow state", which is a bigger decision; PC-148 (consistency check) would shrink to checking that the projection matches the database.
- Earlier today the same topic was discussed as a store with transition rules, a gate holding the credential, and a separate account for the interactive session; the common point is that every actor acts as the same login.
