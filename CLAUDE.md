# Working rules

Project cockpit is a light-weight, opinionated viewer over GitHub for agent-assisted projects. It is NOT another project management system.

- Principles: Purity, Frugality, Brevity. Every line must be required by `docs/constitution.md` or the user's words; prefer deleting to generalising.
- Stdlib only. No token storage: the app acts as the `gh` login.
- Read-only unless `--steer`.
- Tests: pytest, pure logic, no network. Logging via `logging`, not print. Explain every shell command.
- No data or names of any consuming project in this repo.
- Open questions for the owner (standing rule, owner, 2026-11-20): every question an assistant has for the owner that is still open is persisted as a GitHub issue in the repository it belongs to (labels `type:decision` and `question`, an embryo, with the question, the options, a recommendation and the provenance block) and is listed by the cockpit for every project it shows (label `question`, open, with its age). An answer is recorded as a comment, the decision is logged, and the issue is closed with a link to that record.
- Documents (owner, 2026-11-20): a memo or ADR that is clearly about one module or sub-module stays with it; generic ones (several modules, or the project itself) get their own generic home and are listed under every module they name, never moved.
- Owner defaults for all projects (owner, 2026-11-20): the list of preferences the owner wants as defaults for every project lives in docs/owner-defaults.md; a new project starts from it.
- Module cards (owner, 2026-11-20): the files that are ambiguous between sub-modules of a module are listed as notes on that module's card, all of them, each with candidates and reason (data: `unsorted` entries with `candidates` in the ambiguity file of the card-metadata contract).
- Authority analysis of tasks (owner, 2026-11-20; a default for all projects): every task is analysed IMMEDIATELY when it is formulated or edited (at filing time, before it is reported filed or can be released; never lazily at release time) for (a) privilege escalation (it needs a privilege the actor lacks) and (b) conformance with the existing ADRs and standing rules (it would contravene one). The analysis state is visible per task: not analysed, clear (date and version of the rule set and ADR list checked against), flagged (with a link to its question), or stale (the task text or the ADR set changed since). A task that is not analysed is not releasable, by automation or by the Submit action. A flagged task gets a concrete question filed as a question issue linked as a blocker; the submission form poses that question, the owner answers it there and releases the task personally, resolving the issue in the same step; release is refused while the question is open. Automation (the boot-filling job and its workers) never releases a flagged task. Workers file a question issue only when an existing ADR or standing rule makes the solution impossible or when they need a privilege they lack, never a task; a design choice inside the existing ADRs is theirs to make. The analysis is a duty of the Orchestrator (the role that orchestrates the agents, the boot-filling job being an incarnation of it): it analyses every task as soon as the task exists, whoever filed it; tasks are created only by the Orchestrator and the Personal Assistant, and each analyses a task it formulates in the same turn before reporting it filed; a plain Worker cannot create tasks and has no duty here (owner, 2026-11-20). The same duty applies to the Personal Assistant (owner, 2026-11-20). The Orchestrator may store the analysis result with the task (a marker comment, the label needs-owner, the linked question issue; never the privileged labels released, priority, deadline, cancelled). Built by the cockpit task PC-35; until then it is applied by hand.
