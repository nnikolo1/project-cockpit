# Working rules

Project cockpit is a pocket-size Swiss Army knife for agent-assisted software development, in a nutshell and opinionated (constitution, Objective): a light-weight viewer over GitHub for agent-assisted projects. It is NOT another project management system. Besides viewing, it has a small element of continuous integration and delivery and of an artefact store for its projects (constitution, owner 2026-11-24).

- Principles: Purity, Frugality, Brevity. Every line must be required by `docs/constitution.md` or the user's words; prefer deleting to generalising.
- Stdlib only. No token storage: the app acts as the `gh` login.
- Steering is the default (owner, 2026-11-24); `--read-only` turns actions off.
- Restarting the running Cockpit service (standing rule, owner, 2026-11-24, for this project only): after a merge of Cockpit code, restart the service yourself without asking (unload and load the launchd job; a kick-start reuses the old definition) and log it in the manual-interventions log; never ask the owner about a restart.
- Tests: pytest, pure logic, no network. Logging via `logging`, not print. Explain every shell command.
- No data or names of any consuming project in this repo.
- Open questions for the owner (standing rule, owner, 2026-11-20): every question an assistant has for the owner that is still open is persisted as a GitHub issue in the repository it belongs to (labels `type:decision` and `question`, an embryo, with the question, the options, a recommendation and the provenance block) and is listed by the cockpit for every project it shows (label `question`, open, with its age). An answer is recorded as a comment, the decision is logged, and the issue is closed with a link to that record.
- Documents (owner, 2026-11-20): a memo or ADR that is clearly about one module or sub-module stays with it; generic ones (several modules, or the project itself) get their own generic home and are listed under every module they name, never moved.
- Owner defaults for all projects (owner, 2026-11-20): the list of preferences the owner wants as defaults for every project lives in docs/owner-defaults.md; a new project starts from it.
- Module cards (owner, 2026-11-20): the files that are ambiguous between sub-modules of a module are listed as notes on that module's card, all of them, each with candidates and reason (data: `unsorted` entries with `candidates` in the ambiguity file of the card-metadata contract).
- Authority analysis of tasks (owner, 2026-11-20; a default for all projects): every task is analysed IMMEDIATELY when it is formulated or edited (at filing time, before it is reported filed or can be released; never lazily at release time) for (a) privilege escalation (it needs a privilege the actor lacks) and (b) conformance with the existing ADRs and standing rules (it would contravene one). The analysis state is visible per task: not analysed, clear (date and version of the rule set and ADR list checked against), flagged (with a link to its question), or stale (the task text or the ADR set changed since). A task that is not analysed is not releasable, by automation or by the Submit action. A flagged task gets a concrete question filed as a question issue linked as a blocker; the submission form poses that question, the owner answers it there and releases the task personally, resolving the issue in the same step; release is refused while the question is open. Automation (the boot-filling job and its workers) never releases a flagged task. Workers file a question issue only when an existing ADR or standing rule makes the solution impossible or when they need a privilege they lack, never a task; a design choice inside the existing ADRs is theirs to make. The analysis is a duty of the Orchestrator (the role that orchestrates the agents, the boot-filling job being an incarnation of it): it analyses every task as soon as the task exists, whoever filed it; tasks are created only by the Orchestrator and the Personal Assistant, and each analyses a task it formulates in the same turn before reporting it filed; a plain Worker cannot create tasks and has no duty here (owner, 2026-11-20). The same duty applies to the Personal Assistant (owner, 2026-11-20). The Orchestrator may store the analysis result with the task (a marker comment, the label needs-manager (the Manager must resolve it) or needs-pa (the Personal Assistant can resolve it), the linked question issue; never the privileged labels released, priority, deadline, cancelled). Built by the cockpit task PC-35; until then it is applied by hand.
- Agent and OS (owner, 2026-11-24, for this project): the project assumes the agent is Claude and the host is macOS, and says so in the README; but keep the code as agnostic about agent and OS as is practical: whatever depends on Claude or macOS lives in a small, named place (the container runtime adapter, the launch command, the image, the host probes), never spread through the logic.
- Workflow (standing rule, owner, 2026-11-24, for this project only): the Workflow (Code tab, formerly the Flowchart) shows the task workflow of the specification and the constitution; whenever it is found to be outdated against them, redraw it in the same change, never leave it stale; tests/test_workflow.py guards it.
- Standing policies (owner, 2026-11-24): (0) the components of the project metadata, incl. code metrics, token usage, etc, are to be refreshed within 24 hours; (1) stale components are refreshed, not only reported, and the daily job spots gaps (a module metric with no data) and files them as tasks; a gap the owner reports is covered by a generalized, project-agnostic test in the same change that fixes it (a staleness report is filed in the repository, but the refresh is the goal); (2) an agent that finds a file (documentation or code) contradicting a standing policy may file a task that counts as released at once, but must not work on that task itself (separation of powers).
- Production (standing rule, owner, 2026-11-24): from now on all tasks are submitted via the Task Queue: a task is filed as an issue, released by the owner, and worked by the Dispatcher's Workers; the assistant files and analyses tasks and merges the results, and does not start its own background agents for new work unless the owner says so. Up to 6 Workers run at once (spec 4a; raising to 10 is de-prioritised, owner 2026-11-24).
- Task Queue's own tasks (standing rule, owner, 2026-11-24): a bug or task about the Task Queue itself (Dispatcher, Workers, image, proxy, specification) is never run through the Task Queue: it carries the label `interactive-only`, the Dispatcher never gives it to a Worker, and the Interactive Session Agent works it outside the queue as a high-priority task, before other work; everything not about the Task Queue goes through the queue.
- Priority among projects (standing rule, owner, 2026-11-24): unless otherwise said, this project (the Project cockpit) is the top-priority project, as a meta-project that provides the bedrock for all projects.
- Testing isolation (standing rule, owner, 2026-11-24, for this project only): a change to isolation or to anything several Worker users share (private namespaces, homes, temp folders, mounts, permissions) is tested with at least two different users acting in turn on the live container, the second meeting what the first left behind, not with one user only (the temp-folder failure of 2026-11-24 passed a one-user test).
- Structure policy (standing rule, owner, 2026-11-24): when more than 30 percent of a module's files are unsorted (kept in the module because they fit no sub-module unambiguously), that is a policy violation: the daily job finds it and files a policy-finding task (released at once; the finder does not work on it) whose work is an analysis of the module's structure that writes suggestions (sub-modules, assignments) for the owner; it never changes the module map itself.

- Policy findings (owner, 2026-11-24): A policy violation identified by the interactive agent may be filed and released by it as a task, to be worked by a background agent (a Worker); the finder itself never works the task, so the separation of powers holds. The release applies only to tasks labelled policy-finding that carry the policy sentence and the evidence, with a trail comment naming the policy (owner, 2026-11-24; amends the policy-finding rule of the same day).

- Merging (constitutional amendment, owner, 2026-11-24): The Interactive Agent has the authority to merge tasks in the state `unmerged`, and does so unprompted. Before merging it verifies (1) that the commit matches the task brief and (2) that it obeys all policies (tests passing included). If both hold, it merges. If no policy is violated and no test fails but the commit does not meet the brief fully, it merges and files a task meant to finish the job. If a policy is violated or a test fails, it does not merge: it formulates a new follow-up task whose work is to remove the existing issues (owner, 2026-11-24, constitutional amendment). The Interactive Agent may delegate the merge to a background agent by supplying it with this brief; for that merge the background agent holds the privileges of the Interactive Agent, so it can merge and formulate tasks; in this way the Interactive Agent can parallelise the merging (owner, 2026-11-24). Merging is parallelised whenever conflicts can be avoided (branches that touch disjoint or cleanly combinable files go to separate merge agents at once; the others are merged in turn) (owner, 2026-11-24, standing policy).

- Daily reports (owner, 2026-11-25): Every project the Cockpit serves has a daily session report (owner, 2026-11-25, constitutional policy): a dated, terse, factual log of what happened that day, in the project's report folder (default `docs/session_reports/session-report-YYYY.MM.DD.md`), opened at the start of a session, appended to at idle moments, and closed out completely when the date changes. It contains the day's token statistics, as granular as the data allows and generated by a script, never typed by hand (totals, per hour, per source, per model, per session, the Workers' proxy usage, the vendor quota readings, the age of each input). The policy harness checks it: a day with activity and no report, or a report without its token statistics, is a violation that files a task.
